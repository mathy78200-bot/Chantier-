# Firebase — règles et index

- Déployer : `firebase deploy --only firestore:rules,firestore:indexes,storage` (config dans `firebase.json` à la racine). **Déployer les règles avant toute nouvelle version de l'application** : chaque document n'accepte que les clés de son entité Dart (`clesX()` dans `firestore.rules`), une clé inconnue fait refuser l'écriture (§9.2).
- Émulateurs : `firebase emulators:start` (auth 9099, firestore 8080, storage 9199, UI activée, `singleProjectMode`).
- Invariants garantis par `firestore.rules` : isolation par `uid` (aucune règle `collectionGroup`), `modePrix` figé (R2), `chantierId == cid` (R4), aucun `delete` physique (R6), quatre statuts (R11), `version + 1` ou archivage seul pour la bibliothèque (R5/§9.9), horodatages `createdAt`/`updatedAt` posés par le serveur, `deletedAt` présent à `null` à la création puis `null` / inchangé / serveur, `storagePath` d'un justificatif sous `users/{uid}/…/justificatifs/{id}.{ext}` (chantier libre, §9.11), bornes miroir des validations client (montants ≥ 0, `nbPersonnes ≥ 1`, `0 ≤ minutesParPersonne ≤ 1440`, `quantitePrevue > 0`, `sizeBytes ≤ 10 Mo`, seuils cohérents).
- Non garanti (§9.10, §9.14) : transitions de statut, quotas de volume, contenu des listes (`sousCategories`, `justificatifIds` : pas de boucle dans les règles), lien Storage ↔ document Firestore, App Check (à activer avant production), fournisseur d'authentification anonyme (à laisser désactivé dans la console), suppression de compte RGPD.
- `storage.rules` : propriétaire seul, JPEG/PNG/PDF, extension cohérente avec le `contentType`, 0 < taille ≤ 10 Mo, `update` autorisé (nouvel envoi au même chemin), aucun `delete`.
- Index : un composite par requête `where('deletedAt', isNull: true)` + `orderBy` ; la corbeille (`isNull: false` → `!= null` + `orderBy('deletedAt')`) n'utilise que l'index simple ; `watchEnAttente` (`deletedAt` + `uploadStatus in`) a son composite.
- Aucun test de règles n'existe encore (§9.2) : à écrire avec `@firebase/rules-unit-testing` sur l'émulateur avant mise en production (scénarios à couvrir en priorité : chaque écriture des repositories `data/`, `deplacerVers` en `WriteBatch`, `save` des paramètres avant `initialiserUtilisateur`).
